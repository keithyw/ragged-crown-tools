# Ragged Crown Tools

Internal editor for the data behind the Ragged Crown game (tile definitions now; zones, items, entities and events later). Go API + MongoDB backend, Next.js frontend. Solo project, localhost only, no auth.

@ARCHITECTURE.md
@DATA-MODEL.md

The architecture doc is the source of truth for how things fit together. Its "Known gaps" section is the owner's tech-debt list: do not fix items from it unless asked.

## How to work with me

I'm an experienced developer (25+ years) who still wants to write code and keep learning. I'm deliberate and a bit stubborn, and I'll change my mind when given a reason.

- **Explain why.** Give the reasoning and the trade-off, not just a verdict. Say when something is only taste.
- **Small, controllable steps.** Prefer a minimal change I can read and test over a large rewrite. Divide and conquer. Build MVPs and see how they feel.
- **Solve the problem in front of us.** Don't refactor, rename, or "clean up" code I didn't ask about. Don't add abstractions for hypothetical future needs. If you notice something that will actually block the current work, mention it briefly and let me decide.
- **Show the diff, don't bury it.** I read every change. Keep edits focused so they're reviewable.
- **Placeholders are intentional.** Copied-over code, stubs and `// TODO` notes are often reminders to myself. Leave them alone unless they're in the way.
- **Say when you're unsure or wrong.** Verify against the code instead of guessing, and tell me when you haven't been able to run something.
- **Keep answers proportionate.** Short question, short answer. I tire easily, so don't pad.

## Safety rules

- Never run destructive commands without asking first: `rm -rf`, `git reset --hard`, `git clean`, force pushes, dropping databases or collections, `docker compose down -v`.
- Never touch MongoDB data or Docker volumes without asking. Never read, print or commit `.env`.
- Don't commit or push. I do that myself.
- Don't install or upgrade dependencies without asking.

## Commands

Backend and database (repo root):

```bash
make docker-up        # MongoDB + Go API on :8080 (needs .env)
make rc-restart       # restart only the API container
```

Frontend (`frontend/`, pnpm only, never npm):

```bash
pnpm dev                    # http://localhost:3000 (webpack)
pnpm exec tsc --noEmit      # the source of truth for type errors
pnpm lint
pnpm exec prettier --write <files>
```

Verify changes with `tsc --noEmit` and `pnpm lint`. Editor squiggles are unreliable here (the repo is a monorepo and Cursor/VS Code sometimes fails to attach files to `frontend/tsconfig.json`). Ignore a squiggle that `tsc` doesn't confirm. The only expected `tsc` error is `Cannot find name 'LayoutProps'`, a Next-generated type.

## Conventions

**Formatting** (enforced by Prettier, config in `frontend/.prettierrc.cjs`): tabs, single quotes, single quotes in JSX, no semicolons, trailing commas, 80 columns.

**Stack versions that trip people up:**

- Next.js 16 (App Router), React 19. Read `frontend/AGENTS.md` and the docs it points to before using Next APIs from memory. In client components read route params with `useParams`, not the `params` prop.
- Zod 4, not Zod 3. Use `error` for custom messages (not `required_error`/`invalid_type_error`). Don't use `z.coerce` with react-hook-form; convert numbers in `register(..., { setValueAs })`.
- Tailwind v4. Class names that are built at runtime must be safelisted with `@source inline(...)` in `globals.css`. Each directive must stay on **one line** with `/* prettier-ignore */` above it, because Prettier's line wrapping breaks Tailwind's parser. The color palette in `lib/types/colorPalette.ts` and those CSS lines must stay in sync.

**Code structure:**

- Almost everything is a client component (`'use client'`). That's intentional.
- Import from the barrels (`@/components`, `@/hooks`, `@/lib/utils`) like the existing code does.
- Use `cn()` from `@/lib/utils` for class merging, and CVA for variants.
- Forms are config-as-code: a zod schema in `src/schemas`, a `FormField[]` array next to the page, rendered by `FormInput`. Extend that pattern rather than hand-writing form JSX.
- CRUD goes through the generic `collectionService` and the generic hooks (`useCollection`, `useCreateRecord`, `useEditRecord`, `useDeleteRecord`). New entities should reuse them.

**IDs (easy to get wrong):**

- `_id` is the MongoDB ObjectID (hex string) generated by the server. It's the technical key for URLs, API calls, React keys and selection state. Users never see it.
- `id` is a user-facing legacy-style identifier (e.g. `T001`). It is for display only and is **never** a key. Zones reference tiles by `_id`.

**Shared types:** `frontend/src/lib/types/map.ts` is hand-copied from the game repo (`ragged-crown`). There's no shared package on purpose. If you change it, say so, because the game's copy needs the same change.

## Gotchas

- Next doesn't always register a **new route folder** while `pnpm dev` is running. Restart the dev server after creating one.
- Import specifiers are case-sensitive in the bundler even though macOS isn't. A wrong-case import like `from 'React'` produces a confusing "invalid hook call". Match file names exactly.
- PUT replaces the whole document. Fields the form doesn't manage get dropped unless merged in (known gap).
- The backend is a deliberately generic store. Domain knowledge (shape, validation, defaults) lives in the frontend. A new collection needs adding to the allow-list in `backend/internal/collection/middleware.go`, and also to `scripts/ensure-indexes.js` and `mcp/src/index.ts`; then run `make db-indexes` and `make sandbox-indexes` (ARCHITECTURE.md section 6.3).
